# ZAM Academy

Hands-on training apps that build understanding before [ZAM](https://github.com/zam-os/zam) keeps it with spaced repetition. Each app is served at `https://academy.zam-os.org/<app>/`. A ZAM cell holds the cards for an app, and every card links back to the lesson it is about.

## How an app and its ZAM cell fit together

The rules come from [ADR 2026-10-19](https://github.com/zam-os/zam/blob/main/docs/adr/2026-10-19-zam-academy-cells.md) in zam-os/zam.

- **The app teaches; the cell keeps.** The cards of a topic live only in `<app>/cell.json`, a KVT tile. An app ships no card list or card export of its own, and app and cell change in the same PR.
- **Cards cite lessons** as `https://academy.zam-os.org/<app>/#lesson=<lesson id>`. The fragment keeps one app = one library topic in ZAM.
- **Lesson ids are a public contract.** Each app's test pins its lesson ids and checks that every card cites an existing lesson.
- **CI installs every cell** into a throw-away library with the published `zam-core` (`scripts/validate-cells.mjs`).
- **History changes require approval.** The catalog builder refuses cells with `replaces` or `retired_items` unless their `replaces-de-by.json` records a valid approval date and documents exactly those changes: every A/B row is replaced by its one named `academy_slug`, a C row is never replaced (it may be retired), and no undocumented `replaces` or `retired_items` exist. CI tests this safeguard; Pages checks it before building or uploading the site. An unapproved proposal therefore blocks publication.
- **Local drafts stay unpublished.** An optional `<app>/publication.json` uses schema `1` and status `local-only`, `preview` or `ready`. The catalog and public registry check exclude `local-only` cells; invalid metadata fails closed, and missing metadata preserves existing behaviour.
- **A preview is published.** A `preview` app is on Pages, in the atlas and in the catalog like a `ready` app, so its cell is released and its ids are a contract. It differs only in what it tells learners: `preview` in `academy.json` and the catalog entry and a visible `zam-preview-notice` in the app, because teacher review and videos are still open. To end a preview, set the marker to `ready`, remove `preview` and the notice; the registry test requires them to agree. Cell validation still checks drafts. The Pages loop refuses local-only or invalid markers before building or copying any app, even if its list accidentally includes a draft. Publication also requires the Pages entry and explicit release authority.
- **Pages publishes** each app, its `cell.json`, and `/catalog.json` (`scripts/build-catalog.mjs`), with the SHA-256 of every cell. ZAM reads the catalog only on a learner's action. ZAM releases bundle a copy of each cell.
- **A cell is released at its first publication,** in the catalog or in a ZAM release. From then on, its item ids, slugs and cited lessons stay stable; changes use `replaces` and raise the version.

CI (`.github/workflows/ci.yml`) tests and builds the apps a pull request or push changed and uploads their offline zips as artifacts: an app is tested when a file in its folder changed, every app when the package jobs of the CI workflow changed or the base commit is unknown (`scripts/changed-apps.mjs`). The `cells` job validates every cell on each run. Pages runs no test suites. Pages (`.github/workflows/pages.yml`) publishes `index.html` plus every app's build on each push to `main`.

## The atlas landing page

Selecting a live package shows its details and an opening link directly below the title. Activating the selected field again opens the package, with a click, Enter or Space. The map hint and the selected field's accessible label describe this action. Selecting another field resets the details panel's scroll position so its opening link stays easy to find.

`index.html` renders a zoomable knowledge atlas (Schulsicht and Weltwissen) from `academy.json`. Fields without a package are shown grey but can still be entered, so a Fach shows which Schularten teach it in that grade. Where a Schulart has no such Fach in a grade (for example Biologie 9 or Geographie 10 at the Realschule), `kein_unterricht` records it with a note and an official source. Such offers are omitted from the map and list even when planned packages are shown. The coverage matrix marks them as "kein Fach" with a dashed outline, an explanatory tooltip and a link to the official source; grades before a subject starts stay "nicht vorgesehen" without that outline. Neither counts as missing. Search and coverage navigation also expand and focus the destination in the list view. App links return to `https://academy.zam-os.org/`, including when an app is opened from an offline zip.

`fachverbunde` defines combined subjects with one canonical id, school, grades and access `paths`. Mittelschule GPG (`gpg`, grades 5–10) is reachable through Geschichte, Politik und Gesellschaft and Geographie in both lenses, the list and the coverage matrix. Each entry is explicitly named Geschichte/Politik/Geographie. The three routes point to one offer: common ancestors and matrix totals count it once, and search returns one package result. Until a package exists, the shared offer remains planned. A future GPG package is registered once with `fach: "gpg"`, its grade and `school: "mittelschule"`; all routes then open the same app and do not create copies of cards or progress.

To register a new package, add an entry to `pakete` in `academy.json` (app folder, Fach, grade, school, lesson and card counts); `node --test scripts/academy-registry.test.mjs` keeps it in sync with the app cells. UML groups several lessons per atom, so its curriculum test checks the registry's lesson count against the app's actual lessons. School types and subject start grades in the registry are a planning scaffold and can be edited freely.

## Privacy

No accounts, cookies, trackers or third-party requests. Learner progress stays in the browser's `localStorage`.
